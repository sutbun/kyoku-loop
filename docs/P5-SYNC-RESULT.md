# P5 同期・復旧 — DEV-11.01-5

P4の実iPhone合格を受け、復習イベント・問題・学習状態のWindows/iPhone同期を実装した。P4の保存先と本人限定HTTPS経路を維持する。2026-11-01（JST）、DEV-11.01-5への更新後に本人から「同期できた」と回答を受領し、Windows側の実受信と再送時の非増殖を確認してP5合格とした。

## 通信と受信確認

phoneの専用APIはdownloadとsyncだけを受け付ける。汎用のWindows APIは公開しない。Tailscale本人ヘッダー・HTTPSホスト・Originの照合を続ける。NAGAの解析依頼や外部の有料操作は含めない。

送信はprotocol 1・元DBの識別子・端末識別子・元イベントを含む。受信側は型、件数、サイズ、対象問題、日時とJST日付、牌、IDと内容の一致を検証する。未来へ24時間を超える記録は日時確認のエラーにし、端末に保持する。1要求は最大5000イベント・20MB、phone HTTP受付は21MB。上限を超えた場合も未送信記録を消さない。

Windowsは取り込み前のバックアップをprivate/app/backups/pre-sync-*へ作り、1トランザクションで全体を検証・保存・再計算する。失敗時は全体を戻し、成功したCOMMIT後にだけ固有IDと元イベントのSHA-256を含む受信確認を返す。同じID・同じ内容の再送は重複追加しない。同じIDで異なる内容は拒否する。

iPhoneは送った元イベントとハッシュ、返された問題・履歴・受信確認を検証し、IndexedDBのトランザクション完了後にだけ未送信を減らす。通信や保存が失敗した場合、受信確認が欠けた場合、通信中に新しい回答が増えた場合は元記録を保持して再試行する。確認済みの元イベントも端末から削除せず、復旧後の再送に使えるようにする。

## 複数端末と順序

元イベントは変更せず、既存SQLiteのreview_events.request内に原本・開始状態・元の要求を保存する。表示用の順序・加算・前後状態を再計算する。SQLiteの版3と列、IndexedDBの版1を維持し、既存データをリセットしない。P4のmode情報がないイベントも読み取る。

同一端末内は操作時の状態リビジョン、取消とその対象、新サイクルとその後の操作の順序を維持する。その制約内で日時→端末→イベントIDの順に確定する。端末時計が戻った場合も、自分の先行操作より先へ後続操作を移さない。

定期復習はJSTの同日・同サイクルで最初に有効な1回だけを加算し、3/7/14/30日・5回卒業・翌日再復習を再計算する。自主練習では加算しない。保留・再開・再学習も同じ状態規則を適用する。同日の別回答や以前のサイクルの回答も、削除せず履歴へ保存する。

取消は直前の有効な対象だけを戻し、別端末の後続記録を上書きしない。適用できない取消・停止状態への操作・古いサイクルの操作なども、元イベントを保存した上で履歴に理由を表示する。受信確認は記録の保存確認であり、すべての操作が復習回数へ加算されたという意味ではない。

## 操作と更新

- 通信回復・起動・画面復帰・新しい未送信の発生時に同期する。失敗時は間隔を延ばして再試行し、画面にも再試行ボタンを示す。ホームの「今すぐ同期」からも実行できる。
- アプリが終了中のiOSバックグラウンド送信は前提にしない。記録を残し、開き直したときに再試行する。Windows停止中の復習は端末内で続ける。
- 同期は途中のクイズを強制終了しない。通信中に進んだ回答を古い応答で置換しない。別端末で現在の問題の状態が変わった場合は、P3と同じ状態変更の表示とスキップを使う。
- DEV-11.01-4からは、通信ありでホームの「アプリ本体の保存を確認」を押し、アプリを完全終了して開き直す。DEV-11.01-5を確認する。サイトデータの消去や問題のリセットは不要。
- 更新後も本体・牌の表示・問題・回答・途中再開はオフラインで利用する。キャッシュ内のHTMLのビルド番号と全素材、問題の再読込検査が通った場合だけ利用可能と表示する。正常な旧版の本体は修復操作で新版HTMLへ上書きしない。新旧が混ざったWorkerの保存は失敗させ、旧版と学習記録を残す。

## バックアップと復旧

WindowsのSQLiteバックアップは、元イベントと派生状態の両方を含む。復元時にも原本から状態を検証する。共有イベントの派生状態だけが後の同期で変わっていても、原本が一致し不足分だけの復元なら誤って分岐扱いにしない。未同期の分岐したバックアップを無断で上書きすることはしない。

空のWindows DBへ復元するときは、元バックアップのDB識別子も引き継ぐ。既存DBの識別子は勝手に変更しない。これにより、iPhoneが確認済みの記録を再送しても復元先で重複を排除できる。

iPhoneの「記録をファイルに保存」は問題・元イベント・途中の進行をJSONとして保存する。新しい保存先では「記録ファイルから復旧」で読み込める。元IDと途中の進行を保ち、受信確認は未確認へ戻して再検証する。復旧先に記録や途中の復習がある場合は上書きしない。

既存データがある場合はWindowsの「学習」→「バックアップと復元」→「端末の記録ファイルを選択」でJSONを選び、追加/登録済み件数を確認して「この記録を追加」。元IDを保って不足分を取り込み、再実行でも増殖しない。元レポートまで失ったWindowsの復旧には、Windows側のSQLiteバックアップも必要。
