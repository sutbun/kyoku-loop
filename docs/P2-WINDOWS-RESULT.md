## 実装

- 既知のNAGA公式URL / report_id、JSON / gzip。HTTPSの正規化先にだけGETし、任意URL、認証情報を含むURL、別ポート、不明なクエリ、転送を拒否する。Cookie・認証・課金・拡張操作はない。
- プレイヤーと基準モデルを選んで登録。元雀魂とのリンクは任意の手動対応であり、自動照合済みの表示にはしない。表示席の番号は1始まり、データの席インデックスは0始まり。
- P0の検証器が各局の変換牌譜とイベントを照合し、判断直前と各収録イベント直後の公開情報だけを投影する。自分の赤牌とツモ、河の鳴かれた牌/リーチ宣言牌、副露・槓の種類と鳴き元、ドラ、本場、供託、点数、自風を保持する。
- 形式はdata_version=[1,0]、naga_version=[2,2]、game_type=0の四麻カスタムに限定。モデル0/1のみを基準として選択可能。モデルごとの34牌種の重みと宣言された推奨を照合する。
- 整数・非負・34値で合計9900〜10000の既知スケールだけを合計100へ換算する。`gap = 100 × (最大重み − 実打牌の重み) / 合計重み`。赤5は評価時のみ通常5と同じ牌種に対応させ、卓面と実打牌は赤を保持する。0分布・未知形式を0補完しない。自身のリーチ宣言済み/成立後の自由選択でない判断も問題化しない。
- gapが正の候補から各局の最上位を先に選び、残りの高順位候補で最大10まで補充し、最終的にgap降順にする。上位最大3件を自動登録し、その他は手動保存/取消できる。単局で候補が少ない場合や全候補が同重みの場合は水増ししない。抽出ルール版を保存する。
- 同じ完全な変換牌譜の集合から対局ID、対局・席・局・打牌順から判断IDを作る。モデルや元レポートのハッシュは別に保持し、別モデルの評価を混ぜない。同一対局/席の自動登録は合計最大3。既存の問題の評価・履歴を上書きせず、再取り込み時も維持する。
- SQLiteと生レポートはGit外の `D:/dev-data/kyoku-loop/private/app/kyokuloop.sqlite3`。読み込み・保存エラーは成功表示にせず、途中の保存失敗はトランザクションで巻き戻す。データ損失を伴うリセット操作は実装しない。

同じ開発ポートの[Vite middleware hooks](https://vite.dev/guide/api-plugin#configureserver)でローカルAPIを提供し、Python標準の[sqlite3](https://docs.python.org/3/library/sqlite3.html)で保存する。追加のネットワークサーバーや依存パッケージは導入していない。Host/Origin/Content-Typeを確認し、クロスサイト要求を拒否する。静的ファイルだけを配布して動くアプリではなく、Node/Pythonとprivate保存先が必要。
