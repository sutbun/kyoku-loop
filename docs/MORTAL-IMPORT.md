# Mortal解析済み結果の取り込み

2026-11-02の本人指示により、NAGA追加連携は保留しMortal対応を先行する。既存NAGAの元データ・問題・履歴・設定は保持する。旧麻雀解析ツールを参照・移植しない。

## 今回の入口

11.05-3では、流局による終局で残った供託を最終点数の照合へ反映する。mjaiと埋込ログの開始供託・成立リーチ・点数差分が一致し、残額が供託と完全に釣り合い、単独トップが確定する場合だけ加算する。同点トップや不明な収支は照合不能のままとし、Helperの元対局の4人点数・本人点数・順位チェックは維持する。解析内容・評価・IDは変更しない。

取得済みMortal JSON / JSON.gzはファイル選択で複数選択し「選択した○件をまとめて登録」で一括登録できる。1回50ファイル・合計100MB・1ファイル20MBまで。対象席と形式をファイルごとに検証し、既存の自動紐付け判定を適用する。一意に照合できないものは未紐付けとして残す。成功・重複・紐付け状態・失敗をファイルごとに表示し、再試行は失敗分だけを処理する。Windowsの一括選択はMortal専用で、NAGAは従来の1件選択でプレイヤーを確認する。

保存牌譜一覧は行左の選択欄と一覧上の「全選択」「選択した○件を削除」で登録だけを削除できる。スマホでは現在の状態フィルターに該当する全件が全選択の対象で、未表示の次ページ分も含む。削除件数を確認して確定する。解析結果・紐付け・復習問題・回答・学習履歴は残す。削除状態は端末内保存・同期・バックアップへ保持し、古い同期で復活させない。同じURLを明示的に追加し直した場合は一覧へ戻す。

指定フォルダからの自動登録と、解析待ち行への直接ドロップにも対応する。設定・元牌譜への後付けリンク・停止/重複防止の動作は [MORTAL-INBOX.md](MORTAL-INBOX.md) を参照する。通常ブラウザで本人が保存したファイルを扱い、既知拒否のHTTP取得へ自動再試行を追加しない。

Windowsの「牌譜を追加」へMortalの結果URLを貼り「レポートを読み込む」。解析済み結果の対象席とモデルを表示し、「このプレイヤーで登録」で確定する。対象席は結果に記載された席に固定し、別席の評価を生成したように見せない。これは本人アカウントの自動特定ではない。NAGAの基準タイプ設定をMortal取り込みで変更しない。

対応URLは作者サイトのprogress（task）、killerducky（dataが同サイトのreportを指すもの）、report JSON。いずれも同じ結果JSONの通常GETへ正規化する。ホスト/HTTPS/パス/識別子/クエリを限定し、Cookie・認証・proxy credential・リダイレクトを使わない。401/403では停止し、本人取得JSONを使う。JSON/JSON.gzの直接選択も可能。HTML結果の解析や未知版の推測対応は行わない。

**実アクセスの制限**: 本人が示した結果は通常のブラウザ閲覧と最初の通常ダウンロードで取得できたが、アプリと同じPython HTTP取得では403となった。この取得処理は停止し、既に得たJSONのファイル入力を実データ検証に使用した。URLの正規化対応を、URL取得の実動作合格とは扱わない。認証情報の持込み・User-Agent偽装・proxy切替・拒否後の反復試行などの回避は実装しない。

今回は実際に確認した **mjai-reviewer 1.5.10 / Mortal / Hanchan / 四麻** のJSON（review、split_logs、mjai_logを含む）を受け付ける。Mortal本体・学習済みモデルは導入しない。この取り込み器は取得済み結果を扱う。通常ブラウザでの順次解析・保存・登録は[独立Helper](MORTAL-BATCH.md)を参照。東風・三麻は今回の対応外。

11.03-3では、iPad Shortcutsの辞書→テキスト出力で観測した全局log配列の重複にも対応する。全split_logのlogがJSON型も含め完全に同じ配列で、配列長が局数に等しい場合だけ、i番目の局へi番目のlogを対応させる。入力を変更せず通常形式へ正規化し、既存の全局・イベント・レビュー照合を引き続き必須とする。混在/部分一致/異なる配列は拒否。正規化後のJSONでIDを作り、通常形式と重複したレポート・回答を作らない。

## 検証と評価

11.05-1では、手牌に同じ牌を持った状態でその牌をツモした局面について、Mortalの`actual_index`が示す候補と実打牌の手出し/ツモ切り表現が異なる場合も、同じ評価上の選択として照合する。候補と実打牌はそのフラグ以外の全フィールドが一致し、直前が本人のツモで、手牌に同じ表記の牌が2枚以上ある場合に限定する。赤牌と通常牌、別actor、別牌、鳴き後、単独の引牌は同一視しない。実打牌と直後のmjaiイベントの完全一致・元牌譜との照合・Q/確率検証は維持する。原本JSON・入力正規化・ID計算・評価値は変更しない。

11.05-2では、加槓後のreview副露を作者の[State::Fuuro定義](https://github.com/Equim-chan/mjai-reviewer/blob/master/src/state.rs)に合わせて読み取る。`consumed`は元のポンの手持ち2枚、`previous_pon_pai`は元の鳴いた牌、`pai`は追加牌であり、全4枚と`previous_pon_target`を独立再生した副露へ照合する。欠落・枚数・牌・元のポン相手の不一致は拒否する。元のJSON・ID・評価値は変えない。

- mjaiイベントを局別の天鳳形式牌譜と照合し、配牌、局情報、点数、ツモ、打牌、鳴き、ドラ、全アクションの消費を確認する。共有のイベント検証器はAIエンジンと分離し、MortalをNAGAの出力へ変換しない。
- 打牌評価を自分のツモ/チー/ポンの巡目・残り牌数へ一意に結び、手牌・副露・実打牌・候補を検証する。未知形式や不整合は部分保存しない。
- 初期対象は打牌のみの選択肢。鳴き/リーチ/和了などとの混合判断、自リーチ後は問題化せず除外数を保持する。
- 赤牌と通常牌の選択傾向を別に扱う。候補重み差は報告されたsoftmax選択傾向の差を百分率の差として示す。Q値と記録温度の整合性も確認する。勝率・期待点数損失とは呼ばない。既存端末形式の34牌種分布は表示互換の集約値で、赤牌を含む候補の選択や差の計算には使用しない。
- 重要局面は従来同様に各局代表を優先して最大10件、自動復習は同一対局/席で最大3問。Mortal問題のIDはエンジンを区別し、既存NAGAの評価と履歴を上書きしない。再取り込みで問題・履歴を増殖させない。
- 回答前の学習APIには推奨・実打牌・重みを含めない。iPhoneの既存オフライン形式・履歴同期・復習期限を使う。SQL版3と既存の端末保存を維持する。11.03-4の端末内登録を有効にした端末だけschema2へ更新する（[iPad単独利用](IPAD-STANDALONE.md)）。Mortalを含む問題セットはpolicy2とし、NAGA表示に固定された旧版が保存を拒否するようにする。新版は既存policy1も読み込める。更新前後で問題や未送信記録をリセットしない。バックアップ検査は保存元からMortalの局面と評価を再構成して照合する。

本人提供の実結果1件では14局、1,355元イベントから1,325表示手順、149打牌評価、重要10件、自動3問を確認。埋め込まれた局別牌譜とreview stateによる照合であり、元の雀魂原本との独立照合や全レポート形式の合格とは区別する。実結果・URL・5判断の個別内容はrepo外privateのみへ保存する。
